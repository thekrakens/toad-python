## Overview

### Problem Statement

Current auto-sync implementation has several issues:
- **Delayed health data updates**: 30-minute sync interval means workout data can be stale for up to 30 minutes
- **Manual Gymaholic export forgotten**: User forgets to export Gymaholic workouts for hours/days, causing missing exercise details
- **No reconciliation for late exports**: If Gymaholic workout is exported days later, it doesn't merge with existing HealthAutoExport workout
- **Inefficient scheduled syncs**: Productivity sync runs every 5 minutes even when nothing changed
- **Emoji logging noise**: Logs are hard to read with excessive emojis
- **No UI feedback loop**: Task/health day icons don't update automatically to show progress

### Goals

- [ ] **G1: Event-Driven Health Sync** - New files in inbox/ trigger immediate processing (<30 seconds)
- [ ] **G2: Late Export Reconciliation** - Gymaholic workouts exported days later properly merge with HealthAutoExport workouts
- [ ] **G3: Unified Daemon** - Single daemon process manages file watching, productivity sync, and UI updates
- [ ] **G4: Improved Directory Structure** - Clear separation: inbox/ → staging/ → processed/ → failed/
- [ ] **G5: Clean Logging** - No emojis, structured format with clear service labels
- [ ] **G6: UI Responsiveness** - Fast updates to task icons, health day icons, and current day indicators

### Non-Goals

- Real-time sync (sub-second latency) - not needed for this use case
- Distributed daemon architecture - single machine is sufficient
- Web dashboard for monitoring - CLI/logs sufficient for now

### Success Criteria

- [ ] **SC1**: Dropping Gymaholic CSV in inbox → Notion updated within 30 seconds
- [ ] **SC2**: Late Gymaholic export (3 days later) → properly merges with existing HealthAutoExport workout
- [ ] **SC3**: Productivity sync only runs when tasks/entries actually change
- [ ] **SC4**: Task icons update within 2 minutes of time entry creation
- [ ] **SC5**: Health day icons update within 30 seconds of workout completion
- [ ] **SC6**: Logs are readable without emojis, clear service labels
- [ ] **SC7**: Failed files moved to failed/ with error details logged

## Architecture

### Single Daemon with Three Threads

**Daemon Process:** `toad-daemon`
- Managed by launchd (macOS) / systemd (Linux)
- Restarts automatically on crash
- Single log file: `~/.toad/daemon.log`
- Shared state/cache between threads

**Thread 1: File Watcher** (event-driven)
- Library: `watchdog` (Python filesystem watcher)
- Monitors 3 directories across 2 iCloud locations:
  - `~/icloud/HealthExport/TOAD_Activity/` (Health Auto Export - activity + body metrics)
  - `~/icloud/HealthExport/TOAD_workouts/` (Health Auto Export - workouts)
  - `~/icloud/TOAD/inbox/gymaholic/` (Gymaholic CSV exports)
- On new file → trigger health processing pipeline
- Runs continuously, reacts to filesystem events

**Thread 2: Productivity Sync** (scheduled, every 5 min)
- Queries Notion for task/entry updates
- Updates Daily Productivity Metrics relations
- Only syncs if changes detected (cache comparison)
- Timeout: 5 minutes

**Thread 3: UI Update** (scheduled, every 2 min)
- Updates task icons (time vs planned)
- Updates health day icons (goal completion)
- Updates current day indicators
- Lightweight, fast updates (<10 sec)
- Timeout: 1 minute

**Thread Coordination:**
- Shared threading lock ensures sequential execution when jobs overlap
- File watcher has highest priority (immediate processing)
- Productivity/UI syncs can wait if health sync is running

### Reconciliation Strategy

**Workout Matching Logic:**

```python
def match_workouts(new_workout: WorkoutData,
                   existing_workouts: List[NotionWorkout]) -> Optional[NotionWorkout]:
    """
    Match new workout against existing Notion workouts.

    Criteria (ALL must match):
    1. Same date (YYYY-MM-DD)
    2. Compatible workout type
    3. Time overlap (start/end within ±30 minutes)
    """
    for existing in existing_workouts:
        if (same_date(new_workout, existing) and
            compatible_type(new_workout.type, existing.type) and
            time_overlap(new_workout, existing, tolerance_min=30)):
            return existing

    return None  # No match, create new workout


def compatible_type(type_a: str, type_b: str) -> bool:
    """Check if two workout types are compatible for merging."""
    TYPE_EQUIVALENTS = {
        "Functional Training": ["Functional Strength Training", "Cross Training"],
        "Traditional Strength Training": ["Traditional Strength Training", "Strength Training"],
        "Functional Training": ["Climbing", "Running", "Hiking"]  # Gymaholic → subsequent cardio
    }

    # Check direct match
    if type_a == type_b:
        return True

    # Check equivalents
    for primary, equivalents in TYPE_EQUIVALENTS.items():
        if type_a in [primary] + equivalents and type_b in [primary] + equivalents:
            return True

    return False


def time_overlap(workout_a: WorkoutData,
                 workout_b: NotionWorkout,
                 tolerance_min: int = 30) -> bool:
    """Check if two workouts overlap in time within tolerance."""
    # Get start/end times for both workouts
    a_start, a_end = workout_a.start_time, workout_a.end_time
    b_start, b_end = workout_b.start_time, workout_b.end_time

    # Check if start times are within tolerance
    if abs((a_start - b_start).total_seconds() / 60) <= tolerance_min:
        return True

    # Check if time ranges overlap at all
    if a_start <= b_end and a_end >= b_start:
        return True

    return False
```

**Merge Strategy:**

When match found:
1. **Gymaholic → Existing HealthAutoExport Workout:**
   - Keep: HealthAutoExport timestamp (more accurate from Apple Watch)
   - Keep: HealthAutoExport calories, HR, duration (measured data)
   - Add: Gymaholic exercise details (sets, reps, weight)
   - Update: Workout summary/notes with exercise list

2. **HealthAutoExport → Existing Gymaholic Workout:**
   - Keep: Gymaholic exercises (primary data)
   - Update: Calories, HR, duration from HealthAutoExport (more accurate)
   - Update: Timestamp if HealthAutoExport more precise

3. **No Match Found:**
   - Create new workout page
   - Standard sync flow

## Implementation Log

### 2026-01-23 - Initial Planning

**Decision:** Single daemon with three threads
**Rationale:**
- Simpler to manage than multiple processes
- Shared state/cache reduces API calls
- launchd/systemd handles process management
- Lower resource overhead

**Alternatives Considered:**
- Multiple separate daemons (rejected: more complex, more overhead)
- Serverless functions (rejected: not suited for file watching)
- Polling-only (rejected: higher latency for health syncs)

**Decision:** Use watchdog library for file watching
**Rationale:**
- Cross-platform (macOS, Linux, Windows)
- Mature library with good documentation
- Event-driven (low CPU usage)
- Supports recursive directory watching

**Decision:** Reconciliation engine with ±30 min tolerance
**Rationale:**
- Handles clock skew between devices
- Matches real-world usage (Gymaholic export ~1 hour after workout)
- Type compatibility allows "Functional Training" → subsequent "Climbing" match

**Decision:** inbox/ → staging/ → processed/failed/ flow
**Rationale:**
- Clear separation of concerns
- Atomic operations (move = success indicator)
- Easy to debug (inspect staging/ for issues)
- Failed files preserved for troubleshooting

## Performance Considerations

### API Usage

**File Watcher Triggered Health Sync:**
- Reconciliation query (workouts for date): 1 call
- Create/update workout: 1 call
- Update Habit Tracker: 1 call
- **Total per file: ~3 calls**

**Productivity Sync (5 min):**
- Query tasks/entries: 2 calls (with caching)
- Update relations if changed: 1-2 calls
- **Total per sync: 0-4 calls** (0 if no changes)

**UI Update Thread (2 min):**
- Query tasks needing icon updates: 1 call
- Batch update task icons: 1 call
- Query health days needing icon updates: 1 call
- Batch update health icons: 1 call
- **Total per update: ~4 calls**

**Daily Estimate:**
- Health syncs: ~10 files/day × 3 calls = 30 calls/day
- Productivity syncs: 288 runs × 2 avg calls = 576 calls/day
- UI updates: 720 runs × 4 calls = 2,880 calls/day
- **Total: ~3,486 calls/day = 2.4 calls/min** ✅ Under 3/sec limit

### Processing Time

**Target Performance:**
- File processing (inbox → Notion): <30 seconds
- Productivity sync: <30 seconds
- UI updates: <10 seconds

**Optimizations:**
- Batch API calls where possible
- Cache comparison to skip unchanged data
- Async file I/O for staging/processed moves
- Connection pooling for Notion API

## Security & Privacy

### Data Handling

**Sensitive Data:**
- Health metrics (weight, body fat, workout details)
- Productivity data (task names, time entries)

**Storage:**
- Original files: Local `~/.toad/` directories (not cloud)
- Parsed data: Notion (user's private workspace)
- Logs: Local `~/.toad/daemon.log`

**Permissions:**
- Daemon runs as user (not root)
- Files inherit user permissions
- No network access except Notion API (HTTPS)
